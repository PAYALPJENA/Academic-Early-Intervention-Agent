# Project Walkthrough

This project predicts whether a student is likely to finish in the High, Medium, or Low academic-risk group, then presents risk and support suggestions in a Streamlit dashboard. The reproducible experiment is driven by `src/pipeline/run_pipeline.py` and the modules under `src/pipeline/`; it reads the raw CSV, derives a target from `Final_Exam_Score`, compares 12 models, and writes metrics, checkpoints, and charts. The pipeline results select CatBoost on validation, and the Streamlit dashboard loads the validation-selected CatBoost pipeline with its tuned thresholds. The legacy HistGradientBoosting estimator and preprocessor remain a conditional fallback.

## 2. Data flow: CSV to results

1. **Load and label.** `run_pipeline.run()` calls `load_dataset()` ([src/pipeline/run_pipeline.py:471–476](src/pipeline/run_pipeline.py#L471)). `src/pipeline/data.py::load_dataset()` reads the configured CSV, calls `assign_risk()`, and derives `Academic_Risk` from `Final_Exam_Score`: below 40 is High Risk, 40–69 is Medium Risk, and 70 or higher is Low Risk. It checks the full-data counts against 25,615 / 411,494 / 62,891 and stops with `ValueError` if they differ ([data.py:11–30](src/pipeline/data.py#L11), [config.py:17–28](src/pipeline/config.py#L17)).
2. **Remove target leakage and identifiers.** `load_dataset()` drops `Student_ID`, `University_Name`, `Home_City`, and `Final_Exam_Score` from `X` before modeling; the exam score is the source of the target, never a model input ([data.py:32–36](src/pipeline/data.py#L32), [config.py:35](src/pipeline/config.py#L35)). `Semester_ID` remains in the dataframe but is not among the preprocessor's selected columns, so scikit-learn's default remainder behavior drops it ([models.py:18–25](src/pipeline/models.py#L18)).
3. **Engineer four features.** `create_engineered_features()` adds `previous_failure_flag`, `study_engagement_score`, `digital_distraction_score`, and `learning_support_score` from existing columns ([features.py:4–28](src/pipeline/features.py#L4)). The dashboard calls the same function, so these calculations are shared ([risk_prediction.py:109–110](src/risk_prediction.py#L109), [risk_prediction.py:134–138](src/risk_prediction.py#L134)).
4. **Make the split.** `split_dataset()` performs two stratified splits with seed 42 to yield 70% train, 15% validation, and 15% test ([data.py:39–59](src/pipeline/data.py#L39), [config.py:74–79](src/pipeline/config.py#L74)). The pipeline records counts and proportions in `results/data_split.json` and records the run setup in `results/config.json` ([src/pipeline/run_pipeline.py:478–503](src/pipeline/run_pipeline.py#L478)).
5. **Tune model settings on validation.** The capped RF and midterm-only LR use dedicated validation searches; the five added models use `tune_extra()`. Each chooses by validation High-Risk F1, with macro F1 as tie-breaker, and saves `rf_tuning.json`, `tuning_midterm_lr.json`, or `tuning_<model>.json` ([src/pipeline/run_pipeline.py:156–220](src/pipeline/run_pipeline.py#L156), [src/pipeline/run_pipeline.py:265–298](src/pipeline/run_pipeline.py#L265), [src/pipeline/run_pipeline.py:330–357](src/pipeline/run_pipeline.py#L330), [config.py:81–111](src/pipeline/config.py#L81)). Deep-model epoch counts are also chosen by validation ([src/pipeline/run_pipeline.py:181–201](src/pipeline/run_pipeline.py#L181)).
6. **Preprocess and cross-validate.** `build_model()` creates a scikit-learn `Pipeline(preprocessor → estimator)` ([models.py:214–219](src/pipeline/models.py#L214)). `run_model_seed()` makes stratified folds from the training partition and calls `fit_and_score()` separately per fold; because the whole pipeline is fitted on each fold's training rows, scaling and encoding are learned inside that fold ([src/pipeline/run_pipeline.py:377–395](src/pipeline/run_pipeline.py#L377), [src/pipeline/run_pipeline.py:70–77](src/pipeline/run_pipeline.py#L70)). A final pipeline is fitted on training rows and scored on validation ([src/pipeline/run_pipeline.py:397–403](src/pipeline/run_pipeline.py#L397)). Deep models instead use a fixed stratified 100,000-row subsample of the training partition; validation and test remain full-sized ([src/pipeline/run_pipeline.py:145–153](src/pipeline/run_pipeline.py#L145), [config.py:105–107](src/pipeline/config.py#L105)).
7. **Save validation and test probabilities.** The final fit writes validation probabilities and test probabilities to compressed `.npz` files so metrics can be rebuilt without retaining the model in memory ([src/pipeline/run_pipeline.py:400–401](src/pipeline/run_pipeline.py#L400), [src/pipeline/run_pipeline.py:428–432](src/pipeline/run_pipeline.py#L428)). **Nuance:** test features are passed to `predict_proba()` and their probabilities are saved before validation selection; test labels and test metrics are not read until after `selection.json` is written ([src/pipeline/run_pipeline.py:428–430](src/pipeline/run_pipeline.py#L428), [src/pipeline/run_pipeline.py:581–621](src/pipeline/run_pipeline.py#L581)). This is not label leakage, but it means “the test set is untouched until selection” is not literally accurate.
8. **Tune decision thresholds on validation.** For every model and seed, `tune_thresholds()` searches the configured 0.05–0.95 grid for `t_high` and `t_low`. A student is High Risk if `P(High) >= t_high`; otherwise Low Risk if `P(Low) >= t_low`; otherwise Medium Risk. It maximizes High-Risk F1 and breaks ties by macro F1. The resulting thresholds and validation metrics are saved to `results/thresholds_validation.json` ([src/pipeline/run_pipeline.py:80–108](src/pipeline/run_pipeline.py#L80), [src/pipeline/run_pipeline.py:556–579](src/pipeline/run_pipeline.py#L556), [models.py:82–88](src/pipeline/models.py#L82), [config.py:93–94](src/pipeline/config.py#L93)).
9. **Select before test scoring.** `run()` ranks the requested models twice from validation means—once with argmax predictions and once with tuned thresholds—and writes the two rankings to `results/selection.json` before calculating test metrics ([src/pipeline/run_pipeline.py:581–601](src/pipeline/run_pipeline.py#L581)). The current selection file names CatBoost for argmax ([selection.json:1–8](results/selection.json#L1)); the same JSON contains both complete rankings.
10. **Score test and aggregate.** Only then does the test-metric loop read test labels, apply argmax and validation-tuned thresholds, and write `test_argmax.json` and `test_tuned_thresholds.json` ([src/pipeline/run_pipeline.py:603–622](src/pipeline/run_pipeline.py#L603)). `compute_metrics()` calculates accuracy, balanced accuracy, macro/weighted F1, per-class precision/recall/F1, ROC-AUC, PR-AUC, and confusion matrices; `mean_std()` summarizes across seeds using sample standard deviation (`ddof=1`) ([metrics.py:17–52](src/pipeline/metrics.py#L17), [metrics.py:59–67](src/pipeline/metrics.py#L59)). `summary_table.json` contains the two model tables and gains over the midterm-only baseline ([src/pipeline/run_pipeline.py:624–669](src/pipeline/run_pipeline.py#L624)).
11. **Write figures and operating points.** The runner makes class distribution, CV, validation, test, confusion-matrix, tuning, PR, and feature-importance figures ([src/pipeline/run_pipeline.py:671–709](src/pipeline/run_pipeline.py#L671)); `run_operating_points()` selects the validation-selected model, chooses F1-optimal and recall-at-least-0.70/0.80 thresholds on validation, then evaluates them on test and writes `operating_points.json` and `operating_points_high_risk.png` ([src/pipeline/run_pipeline.py:224–253](src/pipeline/run_pipeline.py#L224), [operating_points.py:20–55](src/pipeline/operating_points.py#L20)).

## 4. Checkpoints, options, and result files

- **Resume behavior:** a completed model/seed is reused when its JSON record and both validation/test prediction files exist. Incomplete CV work resumes by reusing individual fold JSON files ([src/pipeline/run_pipeline.py:360–395](src/pipeline/run_pipeline.py#L360)). CPU folds live under `results/runs/folds/`; CUDA folds are kept separately under `results/runs/folds/cuda/` ([src/pipeline/run_pipeline.py:380–388](src/pipeline/run_pipeline.py#L380)). Added-model tuning saves a partial grid-point checkpoint in `results/runs/tuning_partial/tuning_<name>.json` and a completed file at `results/tuning_<name>.json` ([src/pipeline/run_pipeline.py:162–175](src/pipeline/run_pipeline.py#L162), [src/pipeline/run_pipeline.py:206–220](src/pipeline/run_pipeline.py#L206)).
- **Device:** `--device cpu|cuda|auto` defaults to CPU. `auto` uses CUDA only if PyTorch imports and reports a CUDA device; explicit CUDA errors if PyTorch or CUDA is unavailable ([src/pipeline/run_pipeline.py:129–142](src/pipeline/run_pipeline.py#L129), [src/pipeline/run_pipeline.py:445–446](src/pipeline/run_pipeline.py#L445)). XGBoost and CatBoost receive the requested device; LightGBM stays on CPU; PyTorch MLP and FT-Transformer move tensors/model to that device ([models.py:163–187](src/pipeline/models.py#L163), [deep.py:37–45](src/pipeline/deep.py#L37)).
- **Time budget:** `--time-budget N` is in minutes and exits with code 3 once the deadline is passed before starting another grid point, CV fold, or final fit. Re-run the same command to resume ([src/pipeline/run_pipeline.py:123–126](src/pipeline/run_pipeline.py#L123), [src/pipeline/run_pipeline.py:449–459](src/pipeline/run_pipeline.py#L449)). It cannot interrupt a fit already in progress, so wall time can exceed the requested number.
- **Root JSON outputs:** `config.json`, `data_split.json`, `rf_tuning.json`, `tuning_midterm_lr.json`, `tuning_xgb.json`, `tuning_lgbm.json`, `tuning_catboost.json`, `tuning_mlp.json`, `tuning_ft_transformer.json`, `cv.json`, `validation.json`, `thresholds_validation.json`, `selection.json`, `test_argmax.json`, `test_tuned_thresholds.json`, `legacy_80_20.json`, `summary_table.json`, and `operating_points.json`. The runner's write sites and order are visible in [src/pipeline/run_pipeline.py:478–503](src/pipeline/run_pipeline.py#L478), [src/pipeline/run_pipeline.py:509–579](src/pipeline/run_pipeline.py#L509), [src/pipeline/run_pipeline.py:581–669](src/pipeline/run_pipeline.py#L581), and [src/pipeline/run_pipeline.py:224–253](src/pipeline/run_pipeline.py#L224).
- **Per-seed files:** `results/runs/<model>_seed<seed>.json`, `..._val_predictions.npz`, and `..._test_predictions.npz`; CV models also have one fold JSON per fold. Each run record contains validation/CV metrics, timing, importance where available, and parameters; predictions are class probabilities plus the class order ([src/pipeline/run_pipeline.py:362–364](src/pipeline/run_pipeline.py#L362), [src/pipeline/run_pipeline.py:374–395](src/pipeline/run_pipeline.py#L374), [src/pipeline/run_pipeline.py:400–432](src/pipeline/run_pipeline.py#L400)).
- **Figures:** `class_distribution.png`, `cv_metrics.png` (if any CV model is run), `validation_metrics_argmax.png`, `test_metrics_argmax.png`, `test_metrics_tuned_thresholds.png`, `confusion_matrices_test_argmax.png`, `confusion_matrices_test_tuned_thresholds.png`, `pr_curves_high_risk_test.png`, `operating_points_high_risk.png`, `rf_tuning_validation.png`, `feature_importance_rf_capped.png`, and `feature_importance_hgb_permutation.png` are written as applicable ([src/pipeline/run_pipeline.py:671–712](src/pipeline/run_pipeline.py#L671), [plots.py:32–47](src/pipeline/plots.py#L32), [plots.py:50–74](src/pipeline/plots.py#L50), [plots.py:77–182](src/pipeline/plots.py#L77)).

`write_json()` opens destination files in write mode rather than writing a temporary file and atomically replacing them, so a process interruption during a JSON write could leave a truncated checkpoint ([src/pipeline/run_pipeline.py:59–63](src/pipeline/run_pipeline.py#L59)). Also, tuning and completed seed records are not keyed by device: tuning JSON is reused if it exists, and a run JSON is reused whenever its paired prediction files exist. The separate CUDA fold directory does not prevent reuse of a completed CPU seed record ([src/pipeline/run_pipeline.py:162–165](src/pipeline/run_pipeline.py#L162), [src/pipeline/run_pipeline.py:362–368](src/pipeline/run_pipeline.py#L362)).

## 5. How the Streamlit dashboard predicts and recommends

`app.py` adds `src/` to the import path and calls `risk_prediction.predict_student_risk()` ([app.py:8–10](app.py#L8)). At module import, `risk_prediction.py` reads `results/selection.json` to identify the validation-selected model (CatBoost), loads the fitted pipeline from `models/pipeline/catboost.joblib`, and retrieves the validation-tuned operating thresholds from `results/thresholds_validation.json` (falling back to `old_models/` only if pipeline artifacts are missing). The form collects 23 student fields and passes them to the predictor.

The predictor checks the original columns, computes the four shared engineered features, and feeds the expected columns to the fitted CatBoost pipeline (which applies its internal OneHotEncoder and StandardScaler transforms). Decision labels are determined using the validation-tuned thresholds ($t_{high}=0.30$, $t_{low}=0.35$ for seed 0, or selected operating points), and CatBoost SHAP feature contributions are computed to explain High-Risk scores.

There are two intervention paths. In the Streamlit app, recommendations are static lists chosen only by predicted risk: High, Medium, or Low ([app.py:695–790](app.py#L695)). The separate command-line helper `generate_intervention()` adds input-based rules: attendance below 75%; any failed course; weekly study under 15 hours; stress at least 7; motivation below 5; and social-media use above 4 hours. Each rule appends its corresponding action ([risk_prediction.py:168–230](src/risk_prediction.py#L168)). The CLI display calls that helper ([risk_prediction.py:383–411](src/risk_prediction.py#L383)); the Streamlit code instead repeats a different set of fixed actions. The score cutoffs 40 and 70 are **label-creation thresholds**, not dashboard intervention triggers ([config.py:20–22](src/pipeline/config.py#L20)).

Run it from `report/` if it is intended to update `report/assets/`; running the README's `python report/figs.py` from the project root targets a different `assets/` directory ([README.md:59–64](README.md#L59)).

## 7. Inconsistencies and fragile points

1. **README release caveats remain.** The README now reflects the completed 12-model comparison and the actual pipeline driver path. The raw dataset is intentionally user-supplied and must not be distributed until its license and privacy status are verified.
2. **Architecture asset needs review.** `report/figs.py` now describes the selected CatBoost pipeline and conditional HGB fallback. The checked-in `report/assets/fig1_architecture.png` was not regenerated during this release-preparation phase, so compare it with the updated generator before replacing the asset or rebuilding the paper.
3. **Static figure code contains hard-coded old results.** `figs.py` hard-codes label counts and the old 80/20 model metrics/feature importances ([figs.py:32–62](report/figs.py#L32)); its Fig. 3 and Fig. 4 outputs are not referenced by the current `build_paper.js`, but rerunning this helper can still create stale image files. The current builder does use its Fig. 1 and Fig. 2 assets.
4. **Some paper numbers are not run-result fields.** The paper builder contains hard-coded dataset descriptions/statistics (including correlations and category percentages) and two dashboard-example prediction probabilities, such as 92.6% and 80.0%; these do not come from `results/*.json` ([build_paper.js:213–246](report/build_paper.js#L213), [build_paper.js:517](report/build_paper.js#L517)). Treat them as manually sourced/demo values and verify them against the archived analysis or saved dashboard behavior before relying on them.
5. **Test protocol wording needs precision.** Test probabilities are generated and saved before `selection.json`; only test labels and test metrics are deferred until after selection ([src/pipeline/run_pipeline.py:428–430](src/pipeline/run_pipeline.py#L428), [src/pipeline/run_pipeline.py:581–621](src/pipeline/run_pipeline.py#L581)). This does not use test labels to tune or select, but it is not a literal “no test access before selection” protocol.
6. **Device provenance and platform comparability are limited.** `results/config.json` records Python and common library versions, but not the actual device; completed run checkpoints and tuning files do not distinguish CPU from CUDA. A later run can therefore reuse a prior run/tuning file after changing devices ([src/pipeline/run_pipeline.py:478–501](src/pipeline/run_pipeline.py#L478), [src/pipeline/run_pipeline.py:162–165](src/pipeline/run_pipeline.py#L162), [src/pipeline/run_pipeline.py:362–368](src/pipeline/run_pipeline.py#L362)). The project combines the original CPU runs with added Colab runs, and CUDA kernels/library versions can yield small numerical differences; the runbook calls out the Python/runtime and CPU/GPU caveats ([COLAB_RUNBOOK.md:169–173](COLAB_RUNBOOK.md#L169)). Keep Colab run logs and bundle metadata with exported results.
7. **Partial outputs are not atomic.** JSON checkpoints are written directly to their final path, so interruption during the write could leave an invalid JSON file ([src/pipeline/run_pipeline.py:59–63](src/pipeline/run_pipeline.py#L59)). A corrupt checkpoint may need manual recovery from its backup or corresponding source artifact.
8. **The model list is configurable.** Passing `--models` with only some names produces selection/tables among only those models; use the default model list for a full comparison ([src/pipeline/run_pipeline.py:436–452](src/pipeline/run_pipeline.py#L436), [src/pipeline/run_pipeline.py:581–600](src/pipeline/run_pipeline.py#L581)).
9. **Dashboard and pipeline alignment.** The pipeline saves complete scikit-learn pipelines under `models/pipeline/`, and the dashboard directly serves the validation-selected CatBoost pipeline with validation-tuned decision thresholds and SHAP explanations, while retaining `old_models/gradient_boosting.pkl` strictly as a backward-compatible fallback ([models/pipeline/catboost.joblib](models/pipeline/catboost.joblib), [src/risk_prediction.py](src/risk_prediction.py)).
10. **Some stored run records have an older schema.** Current code records `training_rows`, while the summary builder falls back to the train split count when that field is missing; compare the original run records with the newly added model records if using them directly ([src/pipeline/run_pipeline.py:374–375](src/pipeline/run_pipeline.py#L374), [src/pipeline/run_pipeline.py:628–633](src/pipeline/run_pipeline.py#L628), [`results/runs/hgb_seed0.json`](results/runs/hgb_seed0.json#L1), [`results/runs/ft_transformer_seed0.json`](results/runs/ft_transformer_seed0.json#L1)).
11. **Descriptive standard deviations are not significance tests.** The code reports across-seed mean and sample standard deviation, without a statistical test for winner differences ([metrics.py:59–67](src/pipeline/metrics.py#L59)).

## 8. Reproduce from scratch

Use a clean copy of the project with an empty `results/`, `figures/`, and `models/pipeline/` output area. These commands are for Windows PowerShell and use Python 3.13, matching the documented environment ([README.md:25–32](README.md#L25)):

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt -r requirements-extras.txt
python src/pipeline/run_pipeline.py --device cpu
```

That runs the default 12-model list, five seeds, and five folds where configured; it may take substantial time. To make resumable chunks, use `python src/pipeline/run_pipeline.py --device cpu --time-budget 30` and rerun the exact same command until it exits with code 0. To use a GPU where the Python environment and booster builds support it, use `python src/pipeline/run_pipeline.py --device cuda --time-budget 30`; LightGBM remains on CPU.

Run the dashboard with `python -m streamlit run app.py` ([README.md:35–39](README.md#L35)). To rebuild the paper, install its Node dependency once with `Push-Location report; npm ci; Pop-Location`, then run `node report/build_paper.js` from the project root; the builder reads current results and figures ([README.md:59–67](README.md#L59), [build_paper.js:9–31](report/build_paper.js#L9)). Rebuilding the PDF is a separate Word/office export step; it is not produced by the JavaScript builder ([README.md:66–67](README.md#L66)).

## 9. Current Dashboard Deployment

The dashboard reads `results/selection.json`, loads `models/pipeline/catboost.joblib`, and applies the CatBoost seed-0 thresholds from `results/thresholds_validation.json`. The fitted pipeline owns preprocessing. Shared feature engineering, class mapping, optional operating points, SHAP explanations, batch scoring, and profile-based support rules are active.

The legacy HistGradientBoosting estimator in `old_models/gradient_boosting.pkl` and its preprocessor are used only if selection metadata or the selected pipeline artifact is unavailable. That fallback uses argmax decisions; it is not the normal CatBoost decision rule.

The saved HistGradientBoosting metrics and original dashboard case study elsewhere in this walkthrough are historical results, not CatBoost predictions. Review them as such when using the experiment tables or report.

This walkthrough is based on the source and artifacts currently present in the project folder; it does not run training or alter the dashboard.
